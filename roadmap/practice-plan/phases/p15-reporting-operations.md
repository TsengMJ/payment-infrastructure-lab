# P15 報表與營運（9 次迭代）

- **對應模組**：#17 Reporting & Operations、#01（商戶使用者與角色）
- **階段目標**：商戶有自己的後台（登入、角色、交易查詢、結算報表）；內部人員有營運後台（KYB 審核、客服工具、break 處理），所有操作有稽核紀錄；報表查詢不拖慢交易資料庫。
- **前置**：P08（審核紀錄）、P09（事件）、P06（結算資料）。
- **結束時的架構**：`ops` 模組（讀多個 schema 的 read model，只讀不寫）；`web/dashboard`（Next.js）；Postgres 讀副本（選做）。

這個階段的重點不是畫面好不好看，而是**誰能看到什麼、誰能做什麼、做了之後留下什麼**。

---

### I-15.01 商戶後台登入

- **目標**：商戶使用者可以註冊、登入（session 或 OIDC），與 API key 是不同的身分機制。
- **為什麼**：API key 是給程式用的，人要有自己的帳號、密碼政策、MFA、登出。
- **不做**：SSO 整合。
- **先想清楚**：
  1. 自己實作登入，還是使用身分服務（例如 Keycloak、Ory）？
  2. 一個使用者可以屬於多個商戶嗎？
  3. MFA 要不要強制？
- **完成條件**：測試：登入、登出、session 過期、密碼錯誤鎖定。
- **常見陷阱**：用 API key 當作後台登入憑證。
- **Survey**：OIDC、session management、Ory Kratos、Keycloak
- **產出**：使用者模型、ADR 0025「後台身分機制」

### I-15.02 商戶使用者角色

- **目標**：角色（owner、admin、developer、support、viewer）與權限；權限在 API 層檢查。
- **為什麼**：商戶的客服人員不應能修改出款帳戶或建立 API key。
- **不做**：自訂角色。
- **先想清楚**：
  1. 哪些操作只有 owner 能做（出款帳戶、刪除商戶）？
  2. 權限檢查放在哪一層？
- **完成條件**：權限矩陣的表驅動測試：每個角色 × 每個操作。
- **常見陷阱**：只在前端隱藏按鈕。
- **Survey**：RBAC、Hyperswitch user roles permission groups
- **產出**：權限矩陣

### I-15.03 交易時間線

- **目標**：一頁看到一筆付款的完整時間線：intent、attempts、PSP 原始狀態、webhook、風控決策、ledger 分錄、對帳結果、商戶通知。
- **為什麼**：客服與除錯最常問的問題是「這筆到底發生了什麼」；架構文件第 6 節要求能重建單筆交易時間線。
- **不做**：全文搜尋。
- **先想清楚**：
  1. 時間線從多個 schema 組合：直接查詢、還是從事件建 read model？
  2. 每個時間點要顯示哪些欄位？哪些需要遮罩？
- **完成條件**：選一筆經歷過逾時、recovery、退款、對帳的付款，時間線完整呈現。
- **常見陷阱**：時間線只顯示 payment 表的狀態。
- **Survey**：event timeline、audit trail UI
- **產出**：timeline API 與頁面

### I-15.04 商戶結算報表

- **目標**：商戶可下載某期間的結算報表：每筆交易的 gross、手續費、平台費、退款、爭議、net，與出款對應。
- **為什麼**：商戶要用這份報表對自己的帳；報表與平台 ledger 必須一致。
- **不做**：自訂報表欄位。
- **先想清楚**：
  1. 報表資料來自 ledger 還是 payment？兩者不一致時以誰為準？
  2. 大量資料的匯出要同步還是非同步產生？
- **完成條件**：測試：報表的 net 加總等於該期間出款金額（扣除 reserve 與負餘額調整）。
- **常見陷阱**：報表直接從 payment 表算，與帳本不一致。
- **Survey**：Stripe payout reconciliation report、async export
- **產出**：報表 API

### I-15.05 內部營運後台與身分分離

- **目標**：內部人員使用獨立的身分與後台；內部操作與商戶操作在權限與網路上分開。
- **為什麼**：內部人員能看到所有商戶的資料，權限濫用的影響比商戶使用者大很多。
- **不做**：VPN 或零信任網路（筆記討論）。
- **先想清楚**：
  1. 內部人員查看商戶資料時，要不要記錄理由？
  2. 內部後台能不能以商戶身分操作（impersonation）？有什麼風險？
- **完成條件**：測試：商戶使用者無法存取內部 API；內部人員每次查看敏感資料都有紀錄。
- **常見陷阱**：內部與商戶共用同一套權限系統，只靠 `is_admin` 旗標。
- **Survey**：internal tools access control、break glass access
- **產出**：內部身分、內部 API

### I-15.06 KYB 人工審核頁

- **目標**：審核人員可以看到入駐申請、vendor 結果、篩查命中，並做出決定（寫入 I-08.09 的審核紀錄）。
- **為什麼**：P08 的人工審核流程需要一個實際可操作的介面。
- **不做**：自動化建議。
- **先想清楚**：
  1. 頁面要顯示多少個資？能否只顯示 vendor 連結？
  2. 同一申請被兩個人同時審核怎麼辦？
- **完成條件**：E2E 測試：審核人員核准一個申請，商戶能力立即生效；審核紀錄完整。
- **常見陷阱**：審核頁把所有個資一次載入。
- **Survey**：case management UI
- **產出**：審核頁

### I-15.07 客服工具與需覆核的手動操作

- **目標**：客服可以查單、重送 webhook、發起手動退款；手動退款需要第二人核准（maker-checker）。
- **為什麼**：客服操作會直接動到錢；權限太大或沒有覆核是內部詐騙的來源。
- **不做**：工單系統。
- **先想清楚**：
  1. 哪些客服操作需要覆核？門檻是什麼？
  2. 覆核者能不能修改金額？
- **完成條件**：測試：手動退款未經第二人核准不會執行；同一人不能自我核准。
- **常見陷阱**：客服工具直接呼叫 PSP，繞過 refund 模組的冪等與上限檢查。
- **Survey**：maker-checker、four-eyes principle
- **產出**：客服工具

### I-15.08 操作稽核紀錄

- **目標**：所有高權限操作（核准、調帳、退款、修改出款帳戶、規則變更、角色變更）寫入 append-only 的稽核紀錄，含操作者、時間、前後值、理由。
- **為什麼**：稽核紀錄是事後調查與合規的基礎；它本身也必須防竄改。
- **不做**：外部 SIEM。
- **先想清楚**：
  1. 稽核紀錄要集中一張表，還是每個模組各自保存？
  2. 怎麼證明紀錄沒有被竄改（雜湊鏈）？
  3. 稽核紀錄裡的個資要遮罩嗎？
- **完成條件**：測試：每種高權限操作都產生紀錄；紀錄不能被修改；雜湊鏈驗證能抓出被改過的紀錄。
- **常見陷阱**：稽核紀錄與業務資料在同一交易外寫入，失敗時遺漏。
- **設計模式**：Append-only、Hash chain
- **Survey**：audit log design、tamper-evident log、hash chain
- **產出**：audit 元件

### I-15.09 報表 read model（含階段檢核）

- **目標**：報表與時間線查詢改用事件建立的 read model（或讀副本），交易資料庫不受報表查詢影響。
- **為什麼**：大範圍報表查詢會鎖住或拖慢交易資料表；架構文件提到報表可能需要獨立的資料管線。
- **不做**：資料倉儲（ClickHouse 等），筆記中比較即可。
- **先想清楚**：
  1. read model 的延遲可以多大？商戶看到的資料比實際晚幾秒是否可接受？
  2. read model 壞掉時怎麼重建？
- **完成條件**：壓測：執行大範圍報表時，付款 API 的 p95 延遲沒有明顯變化；read model 可以從事件完整重建。
- **常見陷阱**：read model 被拿來做寫入決策。
- **設計模式**：CQRS read model
- **Survey**：CQRS read model、Postgres read replica lag、Hyperswitch analytics ClickHouse
- **產出**：read model、`docs/notes/p15-review.md`
