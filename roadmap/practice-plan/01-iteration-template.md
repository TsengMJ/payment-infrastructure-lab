# 迭代、學習筆記、ADR、階段檢核模板

## 1. 迭代格式（階段文件裡每一次迭代都長這樣）

```markdown
### I-05.03 Journal 借貸平衡檢查

- **目標**：做完後能證明的一件事，只有一件。
- **為什麼**：這個設計在付款系統裡是在防什麼問題。
- **不做**：這次明確不碰的東西，避免範圍膨脹。
- **先想清楚**：
  1. 2–4 個方向題，實作前自己 survey 並寫下答案。
- **完成條件**：可執行的測試或可觀察的證據。
- **常見陷阱**：容易做錯或想錯的地方。
- **設計模式**：（選填）這次會用到的系統設計模式，詳見 03-design-patterns.md。
- **Survey**：關鍵字，詳見附錄。
- **產出**：程式、測試、學習筆記；需要時加 ADR。
```

「設計模式」只出現在重要的迭代。有這一行時，學習筆記要多回答一題：這個模式在這裡解決什麼，代價是什麼，有沒有更簡單的做法。

### 判斷一次迭代是不是太大

符合任何一條就拆開：

- 「目標」需要用「和」連接兩件事。
- 完成條件超過 4 條。
- 需要同時改兩個以上模組的資料表。
- 預估超過 4 小時。

拆的時候，在原編號後加字母，例如 `I-05.03a`、`I-05.03b`，不要重新編號。之後要插入新的迭代也用同樣的方式（計劃裡的 I-02.05a、I-02.05b、I-03.06a、I-05.11a 就是這樣加進來的）。

## 2. 學習筆記

每次迭代一份，放在 `docs/notes/I-05.03.md`。

```markdown
# I-05.03 Journal 借貸平衡檢查

## 我原本以為
（開始前的理解，錯了也照寫）

## 先想清楚的問題與答案
1. 問題：
   答案：
   來源：（官方文件、書、程式碼連結）

## 我做了什麼決定，為什麼
- 決定：
- 放棄的選項與理由：

## 測試證明了什麼
- 測試名稱：證明的不變量

## 還不懂 / 之後要查
-

## 用一句話向面試官解釋
```

「還不懂」不要留空。如果真的都懂了，寫一個你覺得面試官會追問、而你還答不完整的問題。

## 3. ADR（架構決策紀錄）

放在 `docs/adr/NNNN-title.md`，編號從 0001 開始。需要 ADR 的情況：

- 影響兩個以上模組的決定
- 之後很難改的決定（資料模型、鎖策略、事件格式、服務邊界）
- 有明確取捨，而你選了其中一邊

```markdown
# 0007 Ledger 使用列鎖而非 Serializable 隔離等級

- 狀態：Accepted（或 Proposed / Superseded by 00xx）
- 日期：
- 相關迭代：I-05.11

## 背景
要解決什麼問題，限制是什麼。

## 選項
1. 選項 A：優點、缺點
2. 選項 B：優點、缺點

## 決定
選了什麼。

## 後果
- 好處：
- 代價：
- 何時要重新評估：
```

## 4. 階段結束檢核

放在每個階段最後一次迭代裡完成，不另算一次迭代。寫在 `docs/notes/<phase>-review.md`。

```markdown

## 架構圖

- [ ] 更新資料表關係圖（新增的表、所屬 schema、唯一約束）
```

## 5. 故障場景證據格式

放在 `docs/evidence/<scenario>.md`，M1 會彙整。

```markdown
# 場景：PSP 已扣款但回應遺失

- Inject：Mock PSP 設定 `succeed_then_drop_response`
- Observe：payment_attempt 狀態、recovery worker 日誌、trace ID
- Expected：attempt 進 UNKNOWN；recovery 查詢後轉為 AUTHORIZED；沒有第二筆 attempt
- Actual：
- Trace / 指令：
- 重跑方式：`make scenario-psp-lost-response`
```
