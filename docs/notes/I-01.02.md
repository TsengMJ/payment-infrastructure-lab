# I-01.02 API key 產生與雜湊儲存

## 我原本以為

整把 key 做 SHA-256 就能當查詢鍵，前綴只是給人看的。密碼用的 argon2 應該也適用。商戶名稱夠辨認，key 不必再有自己的名字。

## 先想清楚的問題與答案

1. 問題：key 格式要不要帶 `key_id`，前綴做什麼？
   答案：Token 固定是 `sk_test_<key_id>_<secret>` 或 `sk_live_<key_id>_<secret>`，總長 74。`key_id` 是 16 byte CSPRNG，secret 是另外 32 byte CSPRNG，兩邊都用 base64.RawURLEncoding。前綴讓人一眼看出這是密鑰以及它的模式，也讓 secret scanning 有固定樣式。base64url 本身含 `_`，所以用固定長度切開，不用 `strings.Split`。
   來源：[Stripe API keys](https://docs.stripe.com/keys)、[GitHub token formats](https://github.blog/2021-04-05-behind-githubs-new-authentication-token-formats/)、ADR 0003

2. 問題：用 SHA-256 還是 bcrypt / argon2？
   答案：SHA-256 雜湊 secret 的原始 32 byte。API key 有 256 bit 熵，威脅是資料庫外洩後被直接拿去用，不是線上猜密碼。argon2 的 salt 讓你無法用索引查出那一列。查詢用 `key_id`，再用 `subtle.ConstantTimeCompare` 比對雜湊。找不到列時仍比對一段同長度的 digest。
   來源：[Go crypto/sha256](https://pkg.go.dev/crypto/sha256)、[subtle.ConstantTimeCompare](https://pkg.go.dev/crypto/subtle#ConstantTimeCompare)

3. 問題：不存明文時，商戶怎麼辨認是哪一把 key？
   答案：存 secret 編碼的最後 4 碼，再加上必填的 `name`（1 到 100 字元，不唯一）。明文只在 `CreateAPIKey` 的回傳字串出現一次。

## 我做了什麼決定，為什麼

- 決定：只有 `active` 商戶可以建立 key。`INSERT ... SELECT` 要求商戶存在且狀態是 `active`。沒插入時再讀狀態：沒有這列是 `ErrNotFound`，不是 active 是 `ErrMerchantInactive`。外鍵 `ON DELETE RESTRICT`，SQLSTATE `23503` 也是 `ErrNotFound`。
- 決定：連線失敗與逾時是 `ErrUnavailable`。其他資料庫錯誤照原樣往上送。這三種都不是 `ErrInvalidAPIKey`。格式錯誤、未知 key、雜湊不符、模式不符才是同一個 `ErrInvalidAPIKey`，錯誤字串不帶 token。
- 決定：token 前綴、資料列 `mode`、呼叫端傳入的 process mode 必須一致。前綴與 process mode 不同就不查資料庫。雜湊比完才檢查資料列的模式。
- 決定：這次沒有建立 key 的 HTTP API，也沒有 `revoked_at`。
- 放棄的選項與理由：把整把 token 的雜湊當主鍵。無法先取出一列再做 constant-time 比較。也放棄 bcrypt。也放棄這次加 pepper；沒有金鑰管理時，遺失 pepper 會讓每一把 key 同時失效。

## 測試證明了什麼

- `TestNewTokenFormatAndIndependence`、`TestParseTokenRejectsMalformed`：兩把 key 的 id 與 secret 都不同；長度、前綴與壞掉的 token 被拒絕，錯誤不含 token。
- `TestNormalizeKeyName`、`TestClassifyStoreErrSeparatesCauses`：空白名稱被拒絕。外鍵違反是 `ErrNotFound`，連線類 SQLSTATE 是 `ErrUnavailable`，都不是 invalid key。
- `TestCreateAPIKeyStoresHashOnly`：資料庫的文字欄位與雜湊裡沒有明文；`last4` 與 SHA-256 對得上；同一商戶可以有兩把有名字的 key；驗證回傳 merchant UUID 與 `active`。
- `TestAuthenticateAPIKeyRejectsWrongSecretAndMode`：改一個 secret byte、亂字串、live token 配 test mode、資料列模式被改掉，都是 `ErrInvalidAPIKey`。live token 配 live mode 可以通過。
- `TestCreateAPIKeyRejectsInactiveAndMissingMerchant`：`suspended` 與 `closed` 不能建立；不存在的商戶是 `ErrNotFound`。
- `TestAPIKeyForeignKeyAndStoreOutage`：直接插入不存在的 `merchant_id` 得到 `23503`。逾期的 context 是 `ErrUnavailable`，不是 `ErrInvalidAPIKey`。

## 還不懂 / 之後要查

SHA-256 沒有 pepper。資料庫連同應用程式設定一起外洩時，攻擊者仍要先有明文 secret 才能呼叫 API，因為我們沒存明文。若只洩漏資料庫，雜湊擋得住。面試官若問「為什麼不加 HMAC pepper」，我能講代價，但還沒有一個金鑰放哪裡的具體做法。

## 用一句話向面試官解釋

API key 是 `sk_test_` 或 `sk_live_` 加上獨立產生的 key id 與 256 bit secret；資料庫只存 key id、secret 的 SHA-256 和最後 4 碼，用 constant-time 比較，而且只有 active 商戶能建立。
