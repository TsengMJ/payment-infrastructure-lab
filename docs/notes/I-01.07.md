# I-01.07 錯誤格式與錯誤碼目錄

## 我原本以為

把 Go 的 `error.Error()` 放進 JSON 的 `message` 最誠實。商戶看 HTTP status 就知道能不能重試。RFC 9457 的 `type` URI 比 Stripe 的 `code` 更標準。

## 先想清楚的問題與答案

1. 問題：欄位要有哪些？
   答案：`error.type`、`error.code`、`error.message`、可省略的 `error.param`、`error.request_id`、`error.retryable`。`request_id` 與 `Request-Id` header 相同。`/healthz` 和 `/readyz` 維持純文字。
   來源：[Stripe API errors](https://docs.stripe.com/api/errors)

2. 問題：哪些錯誤可以讓商戶重試？要不要在回應裡明說？
   答案：要明說。400、401、403、404 是 `retryable: false`。500 與 503 是 `retryable: true`，只表示同一請求可以再送一次，不表示付款已失敗。之後動帳仍要同一把 Idempotency-Key。
   來源：I-01.03 的狀態碼、實踐計劃 P03

3. 問題：內部錯誤要露出多少資訊？
   答案：固定句子。`Write` 只接受錯誤碼，沒有把 `error.Error()` 寫進正文的函式。未知的碼也改寫成 `internal_error`。SQL 和 token 只留在日誌。
   來源：[RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) 是放棄的選項：付款整合看的是穩定的 `code`，不是 problem type URI。

## 我做了什麼決定，為什麼

- 決定：目錄在 `docs/api/errors.md`，碼的來源是 `internal/platform/apierror`。測試要求每個碼都出現在文件裡。
- 決定：格式不對的 key id 是 400 `parameter_invalid`，`param` 是 `key_id`。格式正確但不在這個 scope 的 id 是 404 `resource_missing`，而且不帶 `param`，所以跨商戶和真的不存在長一樣。
- 決定：503 用 `service_unavailable`，不再和 500 共用 `internal_error`。401 仍帶 `WWW-Authenticate: Bearer`。
- 放棄的選項與理由：RFC 9457。也放棄把內部錯誤原文回給商戶。

## 測試證明了什麼

- `TestErrorResponsesShareOneShape`：驗證、認證、找不到、內部錯誤四種回應欄位一致。內部錯誤正文沒有 `SQLSTATE` 或 key。
- `TestWriteUsesOneShape`、`TestInternalErrorHidesTheCause`：未知的碼不會被原樣寫出。
- `TestCatalogListsEveryCode`：文件列出每一個碼。
- `TestCrossTenantResourcesAreHidden`：跨商戶和未知 id 的 404 正文相同，碼是 `resource_missing`。
- `TestBearerMiddleware`：401、403、503、500 使用同一份物件。503 是 `service_unavailable`。

## 還不懂 / 之後要查

`retryable: true` 的 500 如果發生在已經送出付款之後，商戶照著重試可能會再打一次下游。這次還沒有付款。P03 要怎麼讓這個旗標和 Idempotency-Key 一起讀，而不是讓商戶只看旗標就重送。

## 用一句話向面試官解釋

商戶看到的每個錯誤都是同一份 JSON，用 `code` 和 `retryable` 決定要不要原樣重試；內部原因留在帶 request id 的日誌裡，不進回應。
