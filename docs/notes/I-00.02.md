# I-00.02 目錄結構與 import 邊界檢查

## 我原本以為

Go 的 `internal/` 就足以守住模組邊界。實際上它只擋得住「import 別人的 `internal/`」；`merchant` import `ledger` 的公開套件在編譯器眼中完全合法。

## 先想清楚的問題與答案

1. 問題：模組對外公開什麼？`internal/<module>/api.go` 與 `internal/<module>/internal/` 的分工？
   答案：`internal/<module>` 這個套件（入口檔是 `api.go`）只放其他模組可以使用的介面與 DTO。實作（repository、handler、狀態機、adapter）放 `internal/<module>/internal/...`，編譯器只允許 `internal/<module>/` 底下的程式 import 它。目前兩者都只有 package 宣告。
   來源：[Go internal packages](https://go.dev/doc/go1.4#internalpackages)、[cmd/go Internal Directories](https://pkg.go.dev/cmd/go#hdr-Internal_Directories)

2. 問題：用 depguard 還是 go-arch-lint？兩者能表達的規則差在哪？
   答案：depguard 以「哪些檔案（glob）不能/只能 import 哪些套件」表達，適合少數層級規則；要表達 15 個模組之間的允許圖，每個模組都要列一份清單。go-arch-lint 以 component 加 `mayDependOn` 表達，沒列的就是禁止，套件沒對應到 component 也會失敗。選 go-arch-lint，理由寫在 ADR 0001。
   來源：[go-arch-lint](https://github.com/fe3dback/go-arch-lint)、[golangci-lint depguard](https://golangci-lint.run/docs/linters/configuration/#depguard)

3. 問題：`internal/platform` 可以放什麼、不可以放什麼？
   答案：可以放與業務無關、每個模組都會用的基礎設施：DB 連線與交易、config、log、otel、outbox、inbox、idempotency 儲存。不可以放任何含業務詞彙的程式（金額規則、狀態轉移、費率、商戶設定）。判斷方法：如果換成另一個非付款的系統還能原封不動使用，才屬於 platform。lint 也保證 platform 不能 import 任何模組，避免它變成繞過邊界的中介。

## 我做了什麼決定，為什麼

- 決定：每個模組一個 component（`internal/<module>/**`，同時涵蓋公開套件與 `internal/` 實作），預設只能依賴 `platform`。
- 決定：`deps` 裡不寫 `platform`；go-arch-lint 不接受空的 `mayDependOn`，沒有條目就代表不能依賴任何 component。
- 決定：`allow.depOnAnyVendor: true`。第三方套件該由哪些模組使用（例如只有 platform 能用 pgx）不在這次範圍。
- 決定：`cmd/api`、`cmd/worker` 先用 `.gitkeep` 佔位，I-00.07 有 `main` 時再加入 component 並設 `anyProjectDeps`。
- 放棄的選項與理由：每個模組拆成「公開」與「實作」兩個 component。實作套件已由編譯器保護，再拆一層只多一倍設定。

## 測試證明了什麼

| 情境 | `make lint` | `go build ./...` |
|---|---|---|
| `merchant` import `ledger/internal`（完成條件） | 失敗：`Component merchant shouldn't depend on .../internal/ledger/internal` | 失敗：`use of internal package ... not allowed` |
| `merchant` import `ledger` 公開套件 | 失敗：`Component merchant shouldn't depend on .../internal/ledger` | 成功（只有 lint 擋得住） |
| `platform` import `merchant` | 失敗：`Component platform shouldn't depend on .../internal/merchant` | 成功 |
| 新增未對應 component 的 `internal/zzunmapped` | 失敗 | 成功 |
| 移除上述檔案 | `OK - No warnings found` | 成功 |

## 設計模式：Modular Monolith、Ports & Adapters

- 這裡解決什麼：Modular Monolith 讓所有模組先共用一個資料庫交易保證資金一致性，同時用 import 規則保留之後拆服務的邊界。Ports & Adapters 決定依賴方向：核心不依賴外部細節。
- 代價：多一份設定與一個工具；開放依賴要改設定檔。
- 更簡單的做法：只分資料夾不檢查，等於沒有邊界。這次只固定目錄與依賴方向；真正的 port 介面等到有 PSP（I-02.05）或資料庫可替換時才定義，避免空介面。

## 用一句話向面試官解釋

模組只能依賴設定檔裡明確開放的邊，實作套件由 Go internal 保護，CI 會擋下任何沒經過設計的跨模組 import。
