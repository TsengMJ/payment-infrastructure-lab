# I-01.03 驗證 middleware 與商戶 context

## 我原本以為

middleware 直接 import merchant，把 `mer_` 字串放進 context。驗證失敗一律 401，包含資料庫掛掉。Redis 應該先拿來快取 key，否則每次請求都查資料庫。

## 先想清楚的問題與答案

1. 問題：key 放在 `Authorization: Bearer` 還是自訂 header？
   答案：只接受恰好一個 `Authorization`，scheme 是 Bearer（大小寫不拘），scheme 和 token 之間恰好一個空格。token 最長 74，跟 I-01.02 的固定長度一樣。重複 header、空 token、超長 token 都是 401，而且不查資料庫。不接受 query string，避免 key 進 access log。
   來源：[RFC 6750](https://www.rfc-editor.org/rfc/rfc6750)、[RFC 9110 authentication scheme](https://www.rfc-editor.org/rfc/rfc9110#name-authentication-scheme)

2. 問題：key 無效、商戶被停用、資料庫故障，分別回什麼？
   答案：無效 key 是 401 `{"code":"invalid_api_key"}`，並加 `WWW-Authenticate: Bearer`。`suspended`、`closed` 與未知狀態是 403 `{"code":"merchant_inactive"}`。連線失敗與逾時是 503，其他非驗證錯誤是 500，兩者正文都是 `{"code":"internal_error"}`，不把 SQL 或 token 寫出去。401 不區分「不存在」和「撤銷」，這次也還沒有撤銷。
   來源：I-01.02 的錯誤分類、[Stripe error codes](https://docs.stripe.com/api/errors)

3. 問題：每次請求都查資料庫會不會太慢？要不要快取？
   答案：這次不快取。`key_id` 是主鍵讀取。Redis 只把 client 的連線、Ping、Close 接上，給以後的限流用。驗證不讀 Redis，啟動時 Ping 失敗只記日誌，`/readyz` 仍只看 Postgres。撤銷還沒做；現在加 TTL 快取，之後會和「撤銷立即失效」衝突。
   來源：ADR 0003、[Cache-aside](../../roadmap/practice-plan/03-design-patterns.md)

## 我做了什麼決定，為什麼

- 決定：`internal/platform/auth` 只認識 `Authenticator` 與 `Identity`。`MerchantID` 是 `uuid.UUID`。`cmd/api` 的 adapter 把 `PAYMENT_MODE` 綁進去，並把 merchant 的錯誤翻成 401 / 503。platform 不 import merchant。
- 決定：Authentication 只證明 key。`CheckMerchantStatus` 是另一個純函式，只有 `active` 放行。Authorization 與 scopes 不做。
- 決定：middleware 掛在 `/v1`。`/healthz` 與 `/readyz` 不需要 key。`/metrics` 改到 `METRICS_ADDR`（預設 `:8081`），只接受 loopback、私網與 link-local。公開埠上的 `/metrics` 是 404。
- 決定：context 只放 merchant 的 UUID。不放 `mer_` 字串，也不在這層做業務判斷。
- 放棄的選項與理由：把狀態檢查寫進 `AuthenticateAPIKey`。驗證成功和「這個商戶現在能不能呼叫」會黏在一起，之後要查歷史時不好拆。也放棄驗證快取。也放棄把 `/metrics` 留在公開埠再用 IP 判斷，因為公開路由根本不該掛它。

## 測試證明了什麼

- `TestBearerMiddleware`：缺 header、重複 header、壞格式、超長 token 都是同一份 401，而且沒呼叫 authenticator。錯 key 是 401 並帶 `WWW-Authenticate: Bearer`。`suspended`、`closed`、未知狀態是 403。store 失敗是 503 或 500，正文沒有 SQL 或 token。有效 key 時 handler 拿到 UUID。
- `TestMiddlewareDoesNotLogTheToken`：把 Authorization 交進既有的日誌遮罩後，輸出沒有完整 key。
- `TestHTTPSpanDoesNotRecordAPIKey`：otelhttp 的 span attribute 與 event 沒有完整 key。
- `TestMerchantAuthenticatorMapsErrors`：invalid key、資料庫不可用、其他錯誤分成三條，identity 是 UUID。
- `TestMetricsIsNotOnThePublicPort`、`TestMetricsAllowsOnlyInternalCallers`：公開 handler 沒有 `/metrics`；公網來源被拒，loopback 與私網可以。
- `TestPingAndClose`、`TestPingFailsWhenRedisIsDown`：Redis client 可以 Ping 與 Close。這兩個測試沒有走 API key 驗證。

## 還不懂 / 之後要查

`/metrics` 用 RemoteAddr 判斷私網。請求若經過一層會改來源位址的 proxy，這個判斷就不再是呼叫端的真實位址。這台 lab 的 Prometheus 是直接連宿主機埠，所以現在成立。前面加了反向代理之後，這個檢查要改成只綁內部網卡，或改成獨立的 scrape 網路。

## 用一句話向面試官解釋

`/v1` 只接受 Bearer API key，middleware 把商戶 UUID 放進 context；無效 key 是 401，停用商戶是 403，資料庫故障不是 401，而 Redis 壞掉不會影響這次的驗證。
