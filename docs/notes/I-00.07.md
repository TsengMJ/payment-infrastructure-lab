# I-00.07 HTTP server 骨架與健康檢查

## 我原本以為

`/healthz` 回 200 就代表可以接流量。也以為優雅關閉是把 listener 關掉，進行中的請求可以不要。

## 先想清楚的問題與答案

1. 問題：liveness 與 readiness 的差別？readiness 要不要檢查資料庫？
   答案：`/healthz` 只表示行程還能回答，不查資料庫。資料庫掛了行程仍該活著，否則編排器會把行程殺掉再重啟，資料庫還是掛的。`/readyz` 做 `Ping`，失敗回 503，呼叫端就不該再送流量。啟動時不 `Ping`：連不上資料庫時 `/healthz` 仍要能回答。啟動也不跑 migration（ADR 0002）。
   來源：[Kubernetes liveness and readiness](https://kubernetes.io/docs/concepts/configuration/liveness-readiness-startup-probes/)

2. 問題：優雅關閉時，正在處理的請求給多少時間？
   答案：預設 10 秒，可用 `SHUTDOWN_TIMEOUT` 改。收到 SIGTERM 後 `http.Server.Shutdown` 不再接新連線，並等待已接上的請求結束。10 秒蓋得住一次還在 handler 裡的請求，又不會讓卡住的客戶端把行程留到部署超時。0 或負值在載入設定時就失敗。
   來源：[http.Server.Shutdown](https://pkg.go.dev/net/http#Server.Shutdown)

3. 問題：用標準庫 `net/http` 還是 chi？
   答案：對外的 REST 用 chi（`github.com/go-chi/chi/v5`）。這次只有兩條路由，chi 的價值是之後的 middleware 鏈不用再換 router。內部服務之間的呼叫留到 P17，用 gRPC 與 Protobuf；現在沒有第二個服務，不加入 proto 或 gRPC server。正式 ADR 留到 P17，不佔用 ADR 0002。
   來源：[chi](https://github.com/go-chi/chi)

## 我做了什麼決定，為什麼

- 決定：chi 只出現在 `cmd/api`。關閉邏輯在 `internal/platform/httpserver`，接收任何 `http.Handler`。`cmd/worker` 只載入設定、寫一行日誌、等到 SIGTERM 或 SIGINT。沒有 HTTP，也沒有 gRPC。
- 決定：兩個 main 先 `godotenv.Load`（不覆蓋已存在的環境變數，檔案不存在就繼續），再 `config.Load`。`config` 套件仍不讀檔。
- 決定：不掛日誌、復原、認證等 middleware。`/slow` 只存在於關閉測試的子行程，正式路由沒有它。
- 放棄的選項與理由：標準庫 `ServeMux`。現在夠用，但 I-01.03 起的 middleware 鏈會再換一次 router。也放棄現在就做 gRPC：沒有呼叫端，空的 server 證明不了契約。

## 測試證明了什麼

- `TestHealthzIgnoresDatabase`：ping 失敗時 `/healthz` 仍是 200。
- `TestReadyzFailsWhenDatabasePingFails`：ping 失敗時 `/readyz` 是 503。
- `TestReadyzOkWhenDatabasePingSucceeds`：ping 成功時 `/readyz` 是 200。
- `TestSlowRouteIsNotPublic`：正式 router 沒有 `/slow`。
- `TestSIGTERMFinishesInflightRequest`：慢請求寫出 `started` 之後送 SIGTERM，回應仍是 `starteddone`，然後行程才結束。
- `TestLoadEnvFileDoesNotOverride`：已存在的環境變數不會被 `.env` 蓋掉；檔案裡的新變數會被載入。缺檔不是錯誤。

## 設計模式

- Composition root：依賴在 `cmd/api` 組裝（設定、日誌、資料庫、router）。測試可以換掉 pinger。代價是 `main` 知道具體驅動（pgx）。更簡單的做法是在 `main` 裡直接 `ListenAndServe`，但關閉與健康檢查就沒有可測的接縫。
- Middleware chain：chi 留著這條路。這次不掛，因為還沒有要對每個請求做的事。空的鏈只是多一層呼叫。
- 優雅關閉：SIGTERM 等到進行中的請求，而不是直接切斷。代價是要設上限，否則一個不回的客戶端會把部署卡住。
- Health check：liveness 與 readiness 分開。代價是多一個端點；合在一起就會在資料庫故障時把行程殺掉。

## 還不懂 / 之後要查

- readiness 失敗時，已經在途的請求（例如正要扣款）該不該被途中的 `/readyz` 影響？關閉與 readiness 是兩件事，但部署時兩者會同時發生。

## 用一句話向面試官解釋

`/healthz` 只證明行程還在，`/readyz` 才查資料庫；收到 SIGTERM 會把已經在處理的請求做完，再退出。
