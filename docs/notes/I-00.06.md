# I-00.06 結構化日誌與敏感欄位遮罩

## 我原本以為

呼叫端在記日誌之前把卡號換成 `***` 就夠了。也以為 `slog` 的 `ReplaceAttr` 會走進 `map` 的每一個鍵。

## 先想清楚的問題與答案

1. 問題：每行日誌必備哪些欄位？
   答案：`time`、`level`、`service`、`request_id`、`trace_id`。`service` 由 `cmd/api` 與 `cmd/worker` 各自傳入，不從環境變數讀，避免兩個行程寫成同一個名字。`request_id` 與 `trace_id` 現在固定是空字串：填 request id 要 middleware，I-00.07 明確不做；trace 是 I-00.09。欄位先在，之後才有值可對。
   來源：[slog](https://pkg.go.dev/log/slog)

2. 問題：遮罩是在寫入時做，還是靠呼叫端自律？
   答案：寫入時做。Handler 看到欄位名稱（不分大小寫）就把值換成 `***`，包含 group 裡的屬性，以及 `map` 裡的鍵。`ReplaceAttr` 不會走進 `map`，所以 map 要自己走一層。呼叫端自律擋不住「把整個 header map 丟進日誌」。
   來源：[HandlerOptions.ReplaceAttr](https://pkg.go.dev/log/slog#HandlerOptions)、[PCI DSS logging](https://www.pcisecuritystandards.org/)（卡號不應出現在日誌）

3. 問題：錯誤要記錄多少細節？
   答案：記錯誤訊息（例如 `issuer timeout`），不記 HTTP request，也不記外部回應 body。body 裡常有卡號、email、token。訊息字串本身不會被掃描；卡號若寫進 message 而不是欄位，這層遮罩看不到。

## 我做了什麼決定，為什麼

- 決定：敏感名稱是 `card_number`、`authorization`、`pan`、`cvv`、`cvc`、`password`、`secret`、`token`、`api_key`。命中就整個值換成 `***`，不是部分遮罩。
- 決定：I-00.05 的 `Config.LogValue` 繼續負責 `database_url`。它的欄位名不在這份名單裡，因為那是「已知設定欄位」，不是「任意物件裡的卡號」。
- 放棄的選項與理由：只在呼叫端包一個 `Redact()`。漏一次就寫進日誌，而且事後收不回來。

## 測試證明了什麼

- `TestRecordHasRequiredFields`：每行都有 `time`、`level`、`service`、`request_id`、`trace_id`。
- `TestRedactsCardNumberAndAuthorization`：頂層 `card_number`、group 裡的 `Card_Number`、header map 的 `Authorization`、巢狀 map 的 `cvv` 與 `api_key` 都變成 `***`；`currency`、`Accept`、`amount`、`ok` 還在。原始卡號與 token 不在輸出裡。
- `TestErrorMessageStaysWhenCardIsRedacted`：`error` 訊息保留，同一行的卡號被遮。

## 還不懂 / 之後要查

- 訊息字串裡的卡號要不要掃？掃了會誤傷（金額、id 裡的連續數字），不掃又擋不住 `logger.Info(card)`。I-00.09 以前要定這條規則。

## 用一句話向面試官解釋

日誌在寫出去的時候依欄位名稱遮罩，所以呼叫端把整個 header 丟進來也不會留下卡號或 Authorization。
