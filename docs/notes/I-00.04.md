# I-00.04 Migration 與每個模組一個 schema

## 我原本以為

Atlas 在付款系統裡比較安全，是因為它會檢查破壞性變更，而不是因為安裝數最多。每個模組一個 schema 只要 `CREATE SCHEMA` 就夠了。down 現在可以留著，等抽出服務時再收回。我以為 `docker://postgres/18/dev` 在官方 image 裡就能用，也以為把 `schemas` 限在自己的模組就不會去動別人的 schema。

## 先想清楚的問題與答案

1. 問題：golang-migrate、goose、Atlas 各自怎麼處理多個目錄？
   答案：三者都是一次指向一個目錄。golang-migrate 與 goose 的版本表預設全庫一份，多目錄要自己改表名，否則版本號會撞。Atlas 的預設是一個資料庫一條歷史；多目錄時每個目錄要有自己的 `revisions_schema`（這裡是 `atlas_merchant`、`atlas_payment`），否則會寫進同一個 `atlas_schema_revisions`。這次選每個模組一個目錄，是為了 P17 可以把歷史跟著 schema 帶走。
   來源：[Automatic schema migration planning](https://atlasgo.io/versioned/diff)、[Applying migrations（revisions schema）](https://atlasgo.io/versioned/apply)

2. 問題：migration 要不要寫 down？在付款系統裡 down 是否真的安全？
   答案：這次不寫 `.down.sql`。`atlas migrate down` 依目前狀態計算反向 plan，並先跑 destructive checks。空 schema 的反向是 `DROP SCHEMA ... CASCADE`，本機試過可以再 `migrate-up` 建回來。有資金資料之後這就不安全：刪掉的列回不來，而且新舊版本會同時在跑。所以 down 只開放到 I-17.03，而且只接受 `127.0.0.1`。
   來源：[Down migrations](https://atlasgo.io/versioned/down)、ADR 0002

3. 問題：誰執行 migration，應用程式啟動時，還是獨立指令？
   答案：只有 `make migrate-up`。啟動時自動跑會讓多個副本搶 lock，也把「改 schema」和「換程式」黏在一起。expand / contract 需要這兩步分開。
   來源：[架構演進：資料邊界](../../roadmap/practice-plan/02-architecture-evolution.md)、[Applying migrations](https://atlasgo.io/versioned/apply)

## 我做了什麼決定，為什麼

- 決定：Atlas 1.3.0，每個模組一個 desired state（`schema/<module>.hcl`）和一個 migration 目錄。理由與放棄的選項在 ADR 0002。
- 決定：本地 image 從 `arigaio/atlas:1.3.0-alpine` 再加上 `docker-cli`。`docker://` 會執行 `docker` 指令；官方 image 的 PATH 裡沒有它，dev database 起不來。
- 決定：`diff.skip.drop_schema = true`。第一次 diff 在只宣告 `merchant` 時產生了 `DROP SCHEMA "public"`。Postgres 自己會建 `public`，不能讓模組的 migration 把它刪掉。
- 決定：`migrate apply --allow-dirty`。`payment` 目錄第一次套用時，資料庫裡已經有 `atlas_merchant`，Atlas 認為資料庫不乾淨而拒絕。這不是 drift，是另一個模組的版本表。
- 決定：`make migrate-down` 撤銷該目錄已執行的全部檔案，不用 `--to-version 0`（資料庫裡沒有版本 0）。host 不是 `127.0.0.1` 時直接失敗。
- 放棄的選項與理由：手寫 `.down.sql`。它會和 up 漂移；Atlas 已經會算反向 plan。也放棄單一 migration 目錄，因為 P17 要切開歷史。

## 測試證明了什麼

- `make migrate-up` 之後，`payment_dev` 有 `merchant`、`payment`、`atlas_merchant`、`atlas_payment`。業務 schema 裡沒有表；版本表只在 `atlas_*`。
- 立刻再跑一次 `make migrate-up`，兩個目錄都印 `No migration files to execute`，exit 0。
- `POSTGRES_HOST=10.1.2.3 make migrate-down` 失敗，訊息是 `migrate-down refuses host 10.1.2.3; only 127.0.0.1 is allowed`，沒有連上那台機器。
- `make migrate-down` 依序 `DROP SCHEMA "payment"`、`DROP SCHEMA "merchant"`。兩個業務 schema 消失；`atlas_merchant` 與 `atlas_payment` 還在。再 `make migrate-up` 可以建回業務 schema。
- desired state 與目錄一致時，`make migrate-diff MODULE=merchant NAME=should_not_exist` 印 `no changes to be made`，沒有新檔案。

## 還不懂 / 之後要查

- schema 裡已經有列的時候，Atlas 的 pre-migration checks 會擋下哪些 `DROP`，哪些還是要人看過 plan 才執行？這次只撤了空 schema。
- I-00.10 想跑 `atlas migrate lint` 時，不登入 Atlas Cloud 還能不能在 CI 裡當必須通過的檢查？

## 用一句話向面試官解釋

每個模組的 schema 由自己的 migration 目錄建立，只用獨立指令執行；本機可以 down，等到新舊版本會同時在跑時就收回，之後的變更只向前。
