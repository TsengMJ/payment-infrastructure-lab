# I-00.09 OpenTelemetry trace 與 metrics 基線

## 我原本以為

有 span 的時候，把 `trace_id` 在 `log.New` 裡寫死成空字串，之後再換掉就好。指標直接用 Prometheus client 註冊，trace 再另外接。

## 先想清楚的問題與答案

1. 問題：`trace_id` 怎麼寫進日誌，讓日誌與 trace 能互相跳轉？
   答案：包一層 `slog.Handler`。`Handle` 時從 `context` 的 span 取出 trace id，有有效 span 才寫入，字串是 32 碼十六進位，與 Grafana Tempo 顯示的相同。沒有 span 時寫空字串，所以啟動日誌與現有單元測試仍是空的。`/healthz` 用 `InfoContext`，handler 才讀得到這個 span。`request_id` 維持空字串，留給 I-01.06。
   來源：[SpanContext](https://pkg.go.dev/go.opentelemetry.io/otel/trace#SpanContext)

2. 問題：資料庫查詢要不要建 span？會不會把 SQL 參數寫進 span？
   答案：這次不建。以後若加，只記操作名稱與耗時，不記 SQL 本文與參數。
   來源：這次的完成範圍

3. 問題：metrics 用 OTel 匯出，還是直接用 Prometheus client？
   答案：用 OpenTelemetry API 產生，Prometheus exporter 掛在 `/metrics`。HTTP span 與請求計數用 `otelhttp` 包住 chi router。Label 是 method、路由模板、狀態碼。`otelhttp` 另外加上 scheme、位址、protocol 這類低基數欄位，不把原始 URL、`payment_id`、`merchant_id`、`trace_id` 放進 label。名稱翻譯固定成底線，Grafana 才能用一般 PromQL 查 `http_server_request_duration_seconds_count`。
   來源：[otelhttp](https://pkg.go.dev/go.opentelemetry.io/contrib/instrumentation/net/http/otelhttp)、[Prometheus exporter translation](https://pkg.go.dev/go.opentelemetry.io/otel/exporters/prometheus)

## 我做了什麼決定，為什麼

- 決定：`OTEL_EXPORTER_OTLP_ENDPOINT` 沒設時，行程仍建立 TracerProvider，日誌仍有 trace id，只是不往外送。有設才以 insecure gRPC 送到 collector。範例值是 `127.0.0.1:4317`。Go SDK 會把這個環境變數當成必須帶 scheme 的 URL，所以讀完後先清掉，再把 host:port 交給 `WithEndpoint`。
- 決定：compose 的 `observability` profile 釘版本：collector `0.157.0`、Tempo `2.10.9`、Prometheus `v3.13.1`、Grafana `13.1.1`。Datasource 用檔案 provision。`make up` 仍只有 Postgres。API 在宿主機跑，Prometheus 抓 `host.docker.internal:8080`。宿主機的 9090 常被本機 proxy 佔用，所以 Prometheus 對宿主機開在 `127.0.0.1:9091`。
- 決定：日誌留在標準輸出。Grafana 只接 Tempo 與 Prometheus。集中收集留給選做的 I-00.09a。
- 放棄的選項與理由：讓 exporter 保留 OTel 的點號名稱。Prometheus 3 收得下來，Grafana 的查詢卻把 `http.route` 當成語法錯誤。

## 測試證明了什麼

- `TestTraceIDMatchesSpan`：帶 span 的 `InfoContext` 寫出的 `trace_id` 等於該 span 的 trace id。
- `TestRequestMetricsUseRouteTemplate`：請求 `GET /payments/pay_123`、路由模板 `/payments/{paymentID}` 時，指標沒有 `pay_123`，也沒有 `payment_id`、`merchant_id`、`trace_id`。`http.route` 是模板。
- 本機：`make up-observability` 後打一次 `/healthz`。標準輸出的 `trace_id` 是 `af5c595cdfd3183982a0b7f0c91f254c`。Tempo 的同一條 trace 是 span `/healthz`、服務 `payment-api`。Grafana 的 Prometheus datasource 查到 `http_route="/healthz"` 的請求數是 1。Grafana 的 HTTP API 看得到 Tempo 與 Prometheus 兩個 datasource；沒有在瀏覽器裡點 Explore。

## 還不懂 / 之後要查

- `otelhttp` 的 histogram 在 Prometheus 裡同時是延遲與請求數（`_count`）。之後若要單獨的 counter，要不要再加一個，還是查 `_count` 就夠。

## 用一句話向面試官解釋

一個 `/healthz` 會產生 span；日誌裡的 `trace_id` 與 Grafana 的 trace 相同；`/metrics` 只按路由模板計數，不把付款 id 放進 label。
