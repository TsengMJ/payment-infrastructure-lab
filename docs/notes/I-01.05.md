# I-01.05 商戶範圍隔離

## 我原本以為

查詢記得加 `WHERE merchant_id` 就夠了。跨商戶應該回 403，讓呼叫端知道這筆資源存在但沒有權限。Postgres Row Level Security 可以之後再補，現在先靠 code review。

## 先想清楚的問題與答案

1. 問題：怎麼讓「忘記帶 merchant_id」變成編譯錯誤或測試失敗，而不是靠記憶？
   答案：租戶查詢的參數是 `tenant.Scope`，欄位不匯出，只能用 `tenant.New` 建立。nil 商戶或不是 test/live 的 mode 會失敗，而且失敗發生在 SQL 之前，回 500，不是 404。`GetAPIKey(ctx, keyID)` 仍是唯一不加範圍的讀取，只給驗證用。`internal/merchant/internal/postgres` 的測試會掃 SQL：對 `api_keys` 的 SELECT、UPDATE、DELETE 必須有 `merchant_id =` 和 `mode =`，允許清單只有那個驗證查詢。
   來源：[OWASP IDOR](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/05-Authorization_Testing/04-Testing_for_Insecure_Direct_Object_References)

2. 問題：跨商戶存取回 403 還是 404？為什麼？
   答案：404，正文與「這筆 id 不存在」相同。403 已經用在 key 有效但商戶不是 active。跨商戶若回 403，等於告訴對方這個 id 存在。同一商戶用 test key 讀 live key 也是同一份 404。列表不回 404，只是不包含別的範圍的列。
   來源：[Stripe errors](https://docs.stripe.com/api/errors)（別的帳戶的物件是 resource missing）

3. 問題：Row Level Security 能幫你什麼？代價是什麼？
   答案：應用程式漏掉 `WHERE` 時，資料庫仍可依 session 裡的商戶擋住列。代價是每個請求都要 `SET` 並在連線還回 pool 前清掉，否則下一個請求會沿用上一個商戶；管理員與 migration 要繞過政策；Go 的函式簽名仍看不出誰忘了範圍。這次不實作 RLS。
   來源：[PostgreSQL Row Security Policies](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

## 我做了什麼決定，為什麼

- 決定：`internal/platform/tenant.Scope` 同時帶商戶 UUID 和 key 的 mode。middleware 在驗證成功後寫進 context。handler 只用 `tenant.FromContext`，不讀 path、query 或 body 裡的商戶或 mode。
- 決定：第一個租戶資源是 `GET /v1/api_keys` 與 `GET /v1/api_keys/{key_id}`。回應只有 `key_id`、`mode`、`last4`、`name`、`created_at`。建立與撤銷不在這次。列表最多 100 筆，cursor 留到 I-01.08。
- 決定：`merchants` 表是租戶本身，維持內部查詢，不上 HTTP。
- 放棄的選項與理由：只在應用程式記得加 `WHERE`。呼叫端可以省略參數。也放棄 403，因為那會確認資源存在。也放棄現在做 RLS。

## 測試證明了什麼

- `TestCrossTenantResourcesAreHidden`：商戶 B 的 key 讀商戶 A 的 API key，與讀一個不存在的 id，狀態和正文都是 404。query 上的 `merchant_id` 和 `mode` 沒有改變 scope。列表只有 B 自己的 key。
- `TestOtherModeIsNotFound`：同一商戶的 test key 讀 live key，與不存在的 id 是同一份 404。自己的 key 回應沒有 secret。
- `TestAPIKeyQueriesFilterMerchantAndMode`：新增的 `api_keys` 讀取若沒有兩個條件，測試失敗。驗證用的 `GetAPIKey` 在允許清單。
- `TestOwnedAPIKeyReadsHideOtherTenants`：真實 SQL 對跨商戶、錯 mode、不存在的 id 都是 `ErrNotFound`。無效 scope 不是 not found。
- `TestListAPIKeysStopsAt100`：101 把 key 只回排序後的前 100。

## 還不懂 / 之後要查

允許清單是函式名稱。若有人把未加範圍的查詢寫進 `GetAPIKey` 函式裡的第二段 SQL，掃描仍會放行。之後資源變多時，這份允許清單要不要改成「檔案裡只准出現一次」，而不是依函式名稱。

## 用一句話向面試官解釋

每一筆租戶查詢都必須帶編譯期看得到的商戶與 mode；別的商戶或另一個 mode 回的 404 與「沒有這筆資料」長一樣，所以不能靠猜 id 確認資源存在。
