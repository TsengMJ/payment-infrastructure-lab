# I-01.01 Merchant 模型

## 我原本以為

商戶 ID 用資料庫的 `uuid` 就夠了，對外再決定要不要加前綴。狀態用 Postgres enum 比較不容易寫錯。預設幣別和允許的支付方式應該一開始就放在 `merchants` 上，不然以後每筆付款都不知道這個商戶用什麼。

## 先想清楚的問題與答案

1. 問題：商戶 ID 用 UUID、ULID 還是帶前綴的字串（例如 `mer_...`）？對外露出時有什麼差別？
   答案：主鍵是 UUIDv7，欄位型別是 PostgreSQL `uuid`。對外字串才是 `mer_` 加同一顆 UUID 的 32 碼小寫 hex，沒有連字號。自增整數不使用，因為下一個 ID 可以猜到別的商戶。純 UUID 在日誌和 API 裡與 payment、refund 長一樣，前綴用來看出資源種類；能不能被猜到取決於 UUIDv7 的隨機部分，不取決於前綴。前綴不進資料庫，之後的 `merchant_id` 外鍵也用原生 `uuid`，不存 `mer_` 字串。UUIDv7 的時間序讓同一個索引的新列比較靠近，代價是 ID 本身帶著大約的建立時間。
   來源：[RFC 9562 UUID Version 7](https://www.rfc-editor.org/rfc/rfc9562#name-uuid-version-7)、[PostgreSQL UUID 型別](https://www.postgresql.org/docs/current/datatype-uuid.html)、[Stripe API：物件 ID 帶有類型前綴](https://docs.stripe.com/api)

2. 問題：商戶狀態有哪些（active、suspended、closed）？狀態會影響哪些操作？
   答案：三個值都放進 `text` 欄位的 CHECK：`active`、`suspended`、`closed`。不用 Postgres enum，之後要加值時不必處理 enum 的遷移順序。這次建立商戶一律寫 `active`，沒有狀態轉移。之後才生效：`active` 可以建立訂單、使用 live key、出款；`suspended` 在 I-01.03 讓 API 回 403，已存在的資料仍可查；`closed` 是終態，不再發生新的資金動作，歷史資料仍可查。
   來源：[PostgreSQL CHECK 約束](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-CHECK-CONSTRAINTS)、[I-01.03](../../roadmap/practice-plan/phases/p01-merchant-gateway.md)

3. 問題：商戶的預設幣別、允許的支付方式要放哪裡？
   答案：這次不建這兩個專用欄位，也不放進 `metadata`。預設幣別是單一值，等 I-01.09 有 Money 與 ISO 4217 再加在 `merchants`。允許的支付方式是會增減的集合，等 P11 再用獨立表，不用 `text[]`。現在加欄位會在型別還沒出現時把形狀凍住。
   來源：[I-01.09 與 P11](../../roadmap/practice-plan/phases/p01-merchant-gateway.md)

## 我做了什麼決定，為什麼

- 決定：`id uuid` 由服務產生 UUIDv7 後寫入，欄位沒有資料庫預設值。繞過服務時不會默默拿到另一種 UUID。
- 決定：`merchant.ID.String` 與 `ParseID` 是唯一的 `mer_` 編解碼處。`ParseID` 拒絕沒有前綴、錯誤前綴、大寫與連字號。其他模組拿 `merchant.ID`，不拿裸字串。前綴編解碼先留在 merchant，P02 出現第二種資源 ID 時再抽出共用函式。
- 決定：之後每張表的 `merchant_id` 外鍵都是原生 `uuid`。這次只有 `merchants`，還沒有外鍵。
- 決定：`contact_email varchar(254)` 可為 NULL，不是唯一鍵。省略或只有空白時寫 NULL。有值時去掉前後空白；超過 254 個字元或沒有 `@` 就拒絕。不檢查信箱能不能寄達。
- 決定：`metadata jsonb NOT NULL DEFAULT '{}'`。這次不接受寫入，插入時省略這個欄位，讓資料庫填上空物件。它是還沒有專用欄位的延伸資料，不是預設幣別或支付方式的替代品。
- 決定：`name` 去掉前後空白後必須是 1 到 200 個字元。名稱與信箱都可以重複。
- 決定：`created_at` 與 `updated_at` 在建立時寫入同一個 `clock.Clock` 時刻。這次沒有更新商戶的操作。
- 決定：SQL 放在 `internal/merchant/internal/postgres`。go-arch-lint 裡 merchant 要能依賴自己，否則公開套件不能 import 這個 store；這和 platform 依賴自己的子套件是同一種規則。Postgres 測試輔助從 `_test.go` 移到 `internal/platform/testutil/postgres.go`，其他套件的整合測試才能呼叫 `Start`。
- 放棄的選項與理由：把 `mer_` 字串當主鍵。外鍵會變成 `text`，每一張表都要重複檢查前綴。也放棄 ULID 當主鍵；底層要跟之後的外鍵共用 PostgreSQL `uuid`。也放棄這次寫狀態轉移、HTTP、幣別與支付方式欄位。

## 測試證明了什麼

- `TestParseIDRoundTrip`、`TestParseIDRejects`：外部 ID 只有 `mer_` 加 32 碼小寫 hex 這一種寫法；`NewID` 產生的是 UUIDv7。
- `TestNormalizeName`、`TestNormalizeEmail`：空白名稱被拒絕；空白信箱變成不寫入；過長或沒有 `@` 的信箱被拒絕。
- `TestCreateAndGetWithEmail`：建立後可以用 ID 查回名稱、`active`、信箱與同一個時間；`String()` 是外部形式；資料庫裡的 `id` 是 uuid，不是 `mer_` 字串；`metadata` 是 `{}`。
- `TestCreateWithoutEmail`：省略信箱時查回來是空的，`metadata` 仍是 `{}`。
- `TestCreateRejectsInvalidFields`：服務在寫入前拒絕非法名稱與信箱。
- `TestGetMissingMerchant`：不存在的 ID 是 `ErrNotFound`。
- `TestStatusCheckConstraint`：直接插入 `nope` 得到 SQLSTATE `23514`；`suspended` 與 `closed` 可以寫入。
- `TestMetadataDefaultsWhenOmitted`：INSERT 不帶 `metadata` 時，讀出來仍是空物件。
- `TestMerchantSchemaExists`：`merchant` schema 還在。表的數量不再在這裡斷言，因為 `merchants` 已經存在。

## 還不懂 / 之後要查

UUIDv7 的高位是時間，所以 `mer_` 字串可以推出這個商戶大約何時建立。對商戶 ID 這是否算洩漏？付款 ID 如果沿用同一種 UUID，洩漏的是交易時間，那個答案會不會不一樣？

## 用一句話向面試官解釋

商戶主鍵和外鍵都是 PostgreSQL 的 UUIDv7；`mer_` 只出現在對外字串，狀態用 CHECK 限制成 active、suspended、closed。
