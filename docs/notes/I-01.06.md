# I-01.06 request_id 與關聯 ID

## 我原本以為

`request_id` 就是 `trace_id`，商戶傳來什麼就寫進日誌。有 span 之後，錯誤回應不必再記一次。

## 先想清楚的問題與答案

1. 問題：request_id 與 trace_id 有什麼不同？兩者都要嗎？
   答案：都要。`request_id` 是給商戶客服引用的支援編號，出現在回應 header `Request-Id`。`trace_id` 是 W3C span 的 32 碼 hex，用來在 Tempo 裡串這次呼叫。商戶看不到 trace id，維運人員用日誌把兩個對上。`request_id` 不放進 Prometheus label。
   來源：[W3C Trace Context](https://www.w3.org/TR/trace-context/)、I-00.09 的日誌欄位

2. 問題：可以信任商戶傳進來的 request_id 嗎？長度與格式要不要限制？
   答案：不完全信任。只接受 1–64 字元的 `[A-Za-z0-9_-]`。空的、空白、換行、超長或其他字元都丟掉，改由伺服器產生 `req_` 加 16 byte。合法的值原樣回傳，讓商戶對自己的日誌。
   來源：[OWASP log injection](https://owasp.org/www-community/attacks/Log_Injection)

3. 問題：之後非同步處理（worker）時，要怎麼保留這個關聯？
   答案：這次不傳給 worker。之後寫 outbox 或訊息時，複製 `requestid.FromContext`。跨服務傳遞留到 P17，不把 request id 當成 traceparent 的替代。
   來源：實踐計劃 I-01.06 的範圍

## 我做了什麼決定，為什麼

- 決定：middleware 掛在 otel 之後、路由之前。先寫回應 header，再放進 context，並設成 span attribute `request_id`。
- 決定：日誌在 `Handle` 時從 context 寫 `request_id`，不再在建立 logger 時寫死空字串。沒有請求的啟動日誌仍是空字串。
- 決定：access log 在 `next` 返回後記 method、路由模板、狀態。`/healthz` 不再自己記一行。不記 `Authorization` 與 body。
- 放棄的選項與理由：把商戶的原始 header 原樣寫進日誌。換行可以偽造第二行日誌。也放棄只用 trace id 當客服編號，因為商戶引用的是自己看到的 header。

## 測試證明了什麼

- `TestRequestIDIsOnHeaderAndSpan`：合法的 `Request-Id` 出現在回應 header 和 span attribute。
- `TestInvalidRequestIDIsReplaced`：空白、換行、超長和非法字元都會換成 `req_` 開頭的新值。
- `TestUnauthorizedLogUsesRequestID`：401 的回應 header、access log 和 span attribute 是同一個 id，日誌有路由模板，而且沒有 API key。`trace_id` 另有值。

## 還不懂 / 之後要查

access log 包住 `ResponseWriter` 之後，如果之後的 handler 要 `http.Flusher` 或 `Hijacker`，這個包裝沒有轉接。現在的路由不用這兩個介面。加了串流或 WebSocket 之後，包裝要轉接底層的介面。

## 用一句話向面試官解釋

每個請求都有商戶看得到的 `Request-Id`，日誌和 trace 用同一個值；商戶傳來的值先限格式，trace id 仍是另外一條用來串呼叫的 id。
