# I-01.04 test / live 模式與 key 輪替

## 我原本以為

test 與 live 應該各跑一個行程，`PAYMENT_MODE` 不對就直接 401。撤銷只要在應用程式不要再發那把 key。有兩把有效 key 的那段時間很危險，應該立刻讓舊 key 失效。

## 先想清楚的問題與答案

1. 問題：test 與 live 的資料要怎麼隔離？
   答案：本階段用同一個資料庫，交易列加 `mode`。商戶主檔共用，沒有 mode。請求的 mode 只來自驗證成功的 API key，不接受呼叫端自己指定。repository 必須帶 Merchant ID 與 Mode，少一列、跨商戶、跨 mode 都是 not found，HTTP 是 404。更強的執行隔離留到有真實資金操作時：live 要獨立的 provider credentials，test 不得做任何真實資金操作。
   來源：[Stripe test mode](https://docs.stripe.com/keys#test-live-modes)、ADR 0004

2. 問題：輪替的時間窗怎麼處理？
   答案：建立新 key 後立刻有效，同一 mode 可以同時有多把未撤銷 key。呼叫端改完部署再撤銷舊 key。撤銷寫 `revoked_at`，不可逆，也不能改 mode。交易提交後，下一筆開始的驗證失敗。已經通過驗證、正在處理的請求不取消。驗證不快取，所以不需要另外做失效。
   來源：[Stripe API key rotation](https://docs.stripe.com/keys#rolling-keys)、ADR 0003

3. 問題：用 test key 存取 live 建立的資源應該回什麼？
   答案：404，跟不存在一樣。回 403 會告訴呼叫端這筆資料存在。反方向也是 404。撤銷與未知 key 則是 401，而且錯誤正文不說是撤銷。
   來源：[Stripe errors](https://docs.stripe.com/api/errors)、I-01.03

## 我做了什麼決定，為什麼

- 決定：`AuthenticateAPIKey` 不再接收行程 mode。前綴與資料列 mode 在雜湊比對之後才檢查，撤銷的 key 走同一個 `ErrInvalidAPIKey`。
- 決定：管理端是 `MANAGEMENT_TOKEN`，路由在 `/internal`，不掛商戶 middleware。P15 之前沒有個別操作者，稽核 actor 固定為 `management`。
- 決定：live key 要 `merchants.live_access`。關掉資格不撤銷既有 live key，也不讓它們在驗證時失敗。
- 決定：建立、撤銷、變更資格與稽核在同一個交易。稽核表與 key 的 mode、`revoked_at` 由 trigger 保護。
- 放棄的選項與理由：用行程 mode 擋另一種 key。那樣跨 mode 會變成 401，完不成「看不到 live 資源是 404」。也放棄驗證快取，以及商戶拿自己的 API key 來發新 key。

## 測試證明了什麼

- `TestRevokeAndLiveAccess`：同一 mode 兩把 key 都能驗證；撤銷提交後下一筆是 `ErrInvalidAPIKey`，另一把仍可用；再次撤銷不改時間、不多一筆稽核；沒有 live access 不能發 live key；關掉資格後舊 live key 仍可用；直接改 mode、清 `revoked_at`、刪稽核都會被拒絕；稽核沒有明文 secret。
- `TestAuthenticateAPIKeyRejectsWrongSecretAndMode`：前綴與資料列 mode 不一致不會通過，而且這筆不一致是插入的，不是 UPDATE。
- `TestInFlightRequestIsNotCancelledWhenLaterAuthFails`：handler 已開始後，後面的驗證失敗不會取消這個請求。
- `TestResourceHidesOtherModesAndMerchants`：query 上的 mode 不會改變 context；test key 讀 live、live key 讀 test、另一個商戶來讀，都是 404。
- `TestTestKeyCannotReadLiveResource`：同一條 SQL 用 Merchant ID 與 Mode 過濾，跨 mode 與跨商戶都是 not found。
- `TestManagementRoutesRejectMerchantKeys`：商戶 key 與錯誤的管理憑證不能建立或撤銷；管理 token 拿去呼叫 `/v1` 是 401 `invalid_api_key`。

## 還不懂 / 之後要查

共享的 `MANAGEMENT_TOKEN` 洩漏時，稽核只看得到 actor `management`，看不出是哪一次部署、哪一台機器發出的。P15 改成個別操作者之後，舊的事件要怎麼和人對上，我還沒有答案。

## 用一句話向面試官解釋

API key 的前綴決定這筆請求是 test 還是 live，交易查詢一定帶商戶與 mode，對不上就是 404；換 key 時兩把可以並存，撤銷寫進資料庫後下一筆驗證就失敗，而且不靠快取。
